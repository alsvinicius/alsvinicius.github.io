02

Principles

WHY IT BEHAVES THIS WAY
P1

One source of truth

Requirements, journeys, decisions and tasks carry stable IDs (REQ, JRN, DEC, TASK). IDs are never reused, so every task traces back to the product value it serves.

P2

No invented decisions

Unknowns stay open questions. A deferred TBD needs an owner, the affected IDs and a revisit point. The agent asks, or records a decision with autopilot on, instead of guessing.

P3

Every change is recorded

Each change to a specification writes a revision entry, and each technical decision gets its own ADR. History is added to, never rewritten.

P4

Checks, not opinions

What a program can check, a program checks: one entry point for format, lint, tests and structural validators, called by git hooks, CI and the validator agent.

P5

Tests first, if you want

The technical definition asks whether to write failing tests before the code. If yes, every task starts with its tests, and the failing tests can be committed first as proof.

P6

Safe by default

No deployment, publication, paid services or security testing without explicit authorisation. You can opt out of the workflow for any single change by saying so.

03

Review and autopilot

BUILT INTO THE FLOW

Two guardrails shape how the agent works: a dedicated agent reviews every change, and you decide how much the agent may decide for you.

Code review

A dedicated Reviewer agent in the harness checks each task after validation, from the specification and the diff rather than from the author’s explanation. It is read-only: it reports findings and never fixes them.

  • Findings carry a severity, a location, the requirement they violate and a concrete failure scenario.
  • A blocker or unwaived major finding stops the task from being done; fixes get at most two rounds before the task is marked blocked.
  • Every review is saved as its own file in docs/reviews/. /review-code also works on any branch or diff, with or without a harness.

Autopilot

Turn it on and the agent runs the whole flow without questions. Wherever it would have asked you, it decides, continues and saves the decision as its own file in docs/autodecisions/.

  • Switch it on or off at any moment with /autopilot, or by editing one field in the workflow state. Turning it off finishes the current action and asks you from then on.
  • Each decision records the question not asked, the options, the choice, the impact and how to reverse it. Technical ones also get an ADR.
  • It never invents numbers, spends money, deploys or skips validation and review; facts only you can supply stay as labelled assumptions.

05

Strengths and trade-offs

AN HONEST ACCOUNT

Strengths

  • Specs and code stay in sync: a standing rule in AGENTS.md or CLAUDE.md routes every change through the workflow, and /reconcile repairs drift.
  • Resumable: state is saved after each answer, so a new session continues where the last one stopped.
  • Agent-ready tasks: each has sources, dependencies, a Definition of Done, validation evidence and a stop condition.
  • MVP first: the minimum testable slice is separated from the rest of the plan.
  • Works on existing repositories: brownfield discovery reads code statically, and as-is mode documents without creating work.
  • Backwards compatible: after a skill update, /upgrade adds what older projects lack and deletes nothing.
  • Reviewed and reversible: a dedicated reviewer checks every task, and every autopilot decision is its own file that you can confirm or reverse.

Trade-offs

  • Overhead: built for products, not one-off scripts. A tiny fix in a project that uses it still touches artifacts unless you opt out.
  • Many small files and approval gates: a deliberate choice for traceability that slows quick exploration.
  • Opinionated structure: Diátaxis docs, ADRs, a DDD domain model and revision logs are mandatory parts of the flow.
  • Structural, not semantic: validators check links, IDs and indexes, not whether a requirement is right. Quality still depends on your answers and the agent.
  • Unbenchmarked: 44 eval cases are written, but no runner is bundled and none has been executed. /upgrade has not been tried on a real legacy project.
  • Enforcement needs activation: git hooks protect only once enabled, so CI is the backstop, and red commits need merges that keep history.
  • Autopilot decides on your behalf, so its choices stay assumptions until you confirm them, and the reviewer is another agent pass, not a human review.

Get started

THREE MOVES
  1. 1

    Add the skill

    Copy skills/product-dev-workflow from the repository into the folder where your coding agent loads skills. It is a folder of Markdown, templates and eval cases; there is no installer or runtime.

    Start a step

    Use a step name or plain words, and say where the project lives. Slash names are routing conventions in your message, not registered commands.

    Follow the handoff

    Each step ends by naming the next one. Say “continue” to resume from the saved workflow state.

07

FAQ

COMMON QUESTIONS
Is this a tool I install?

No. It is a skill: instructions, templates and evaluation cases that a coding agent reads and follows. It has no runtime of its own.

Which agents does it work with?

It is written for coding agents that load skills from a folder with a SKILL.md entry point. Agent definitions adapt to the host's format; if the location is unknown, the skill asks once.

Does it write the application code?

Only /mvp and /execute do, and only within the approved plan. Every other step writes documents.

Does the reviewer fix problems?

No. The Reviewer agent is read-only. It reports findings with evidence, and the Executor or you fix them. A task is not done while a blocker or unwaived major finding is open.

Will it interrogate me?

It asks one to three focused questions per batch and reuses earlier answers. With autopilot on, which you must request explicitly, it saves each question it would have asked as a decision in docs/autodecisions/.

Can I turn autopilot on and off?

Yes, at any moment. Say so, use /autopilot on or off, or edit the Autopilot field in the workflow state. Turning it off finishes the current action, lists the decisions taken and asks you from then on. Nothing already decided is undone; you can confirm or reverse each decision.

Can I skip the workflow for one change?

Yes. Say so explicitly. The artifacts are left untouched, the agent tells you they are out of sync, and /reconcile can recover the change later.

What about a project that already exists?

Use /brownfield-discovery. It reads the repository statically, separates facts from inferred intent, and in as-is mode records what exists without creating tasks.

I updated the skill. What happens to old projects?

Run /upgrade. It detects each capability from the project's contents, shows a plan, and only adds missing structure. Nothing is deleted, renamed or renumbered.

Does it deploy or spend money?

No. Deployment, publication, paid services, production data and security tests outside the approved harness all need explicit authorisation.

Is test-first development mandatory?

No. The technical definition asks, with a recommendation. You can choose tests alongside the code, or defer the decision.

Which language are the documents written in?

The language you use for the workflow, kept consistent across artifacts. Code identifiers and quoted source text stay as they are.
